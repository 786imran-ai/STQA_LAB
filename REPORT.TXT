CHAPTER 1: INTRODUCTION
================================================================================

1.1 INTRODUCTION
Software Testing and Quality Assurance (STQA) is a critical engineering 
discipline within the software development life cycle (SDLC). The primary goal 
of software testing is not merely to discover bugs, but to systematically assess 
conformance to functional and non-functional requirements, verify system 
correctness, validate operational reliability, and measure software quality 
against objective metrics.

TestLab is a full-stack, web-based Software Testing and Quality Assurance 
platform developed to demonstrate, execute, and verify all fundamental software 
testing methodologies through real, working software systems. Rather than 
treating testing as a theoretical checklist or using isolated toy scripts, 
TestLab bridges the academic curriculum and real-world industrial practice by 
integrating two fully operational software products:
1. A multi-user To-Do List Management System (used for functional, integration, 
   API, regression, performance, and UI automation testing).
2. A Student Result Management System (used for requirements analysis, 
   equivalence partitioning, boundary value analysis, and white-box coverage).

The platform centralizes ten independent laboratory experiment workspaces 
modeled strictly after the university STQA curriculum. Each experiment 
workspace includes an Aim, Objectives, Theoretical Background, Laboratory 
Procedure, Test Case Matrix, Interactive Execution Sandbox, and Results 
Evidence with downloadable IEEE 829-style PDF documentation.


1.2 BACKGROUND
In modern software engineering, software systems have transitioned from monolithic 
offline desktop applications to distributed cloud-native services. High-profile 
software failures—ranging from financial transaction glitches to aerospace control 
crashes—have demonstrated that software bugs can cause catastrophic financial, 
reputational, and physical damage. Consequently, industrial engineering standards 
demand continuous testing, automated regression verification, shift-left testing, 
and measurable test coverage before code deployment.

Traditionally, software testing laboratory courses in academic institutions 
have relied on disparate, standalone Python or C++ scripts executed in isolated 
terminal windows. Test cases are typically typed manually into static Word 
documents or Excel spreadsheets. Actual outputs are rarely correlated with live 
database states, defect management tools are simulated on paper, and automated 
browser testing tools like Playwright or Selenium are taught abstractly without 
real application targets. TestLab modernizes this paradigm by embedding real 
production libraries (FastAPI, SQLite, Pytest, Playwright, Coverage.py, ReportLab) 
into a cohesive, web-based laboratory platform.


1.3 PROBLEM STATEMENT
Conventional software testing laboratory pedagogy suffers from the following 
inherent deficiencies:
1. Fragmentation: Laboratory experiments are isolated into disconnected programs, 
   preventing students from understanding how unit tests feed into integration 
   tests and full system validation.
2. Static and Mocked Results: Students often record theoretical results without 
   observing actual runtime behavior, exception flows, or boundary failures.
3. Lack of Defect Lifecycle Realism: Defect reporting is taught on paper, failing 
   to demonstrate the dynamics of state transitions (New -> Assigned -> Open -> 
   Fixed -> Retest -> Verified -> Closed) and the critical retest failure loop.
4. Absence of Authentic Automation: Students memorize automation syntax without 
   seeing a headless browser interact with DOM elements, handle HTTP cookies, 
   or capture visual screenshot evidence.
5. Inconsistent Documentation: Academic test reports lack adherence to formal 
   industrial standards such as IEEE 829.

TestLab directly solves these problems by providing an integrated, persistent, 
and reproducible testing laboratory where every button, form, test runner, and 
calculation operates against real code and genuine database records.


1.4 OBJECTIVES
The central objectives of the TestLab project are:
1. To develop a robust, full-stack web platform using FastAPI and SQLite that 
   serves as an educational and industrial software testing workbench.
2. To build an operational To-Do List Management System featuring full CRUD, 
   priority levels, status workflows, search, and user-level data isolation.
3. To build an operational Student Result Management System enforcing rigorous 
   0–100 mark boundaries, percentage algorithms, syllabus grading rubrics 
   (A, B, C, D, F), and multi-subject pass/fail logic.
4. To implement all 10 software testing laboratory experiments as independent, 
   self-contained workspaces accessible without completion gating.
5. To execute genuine Pytest unit, integration, API, and regression test suites 
   through backend subprocess runners without hardcoded values.
6. To implement automated browser testing using Playwright in headless Chromium, 
   verifying UI workflows and capturing screenshot evidence.
7. To provide authentic white-box statement and branch coverage measurement 
   using Coverage.py on Python AST execution paths.
8. To demonstrate the complete 7-stage defect lifecycle on an interactive 
   Kanban board with automated retest failure handling.
9. To compute real-time Software Quality Assurance (SQA) metrics, including 
   Defect Density, Defect Arrival Rate, and Developer Productivity.
10. To automatically compile downloadable IEEE 829-standard PDF reports for 
    every individual experiment and the comprehensive final project.

CHAPTER 2: LITERATURE SURVEY
================================================================================

2.1 OVERVIEW
The literature on software engineering, verification, and validation provides 
a rich body of methodologies, standards, and empirical studies:

1. Software Testing Foundations (Pressman, Sommerville, Myers):
   Glenford Myers in "The Art of Software Testing" established that testing is 
   the process of executing a program with the intent of finding errors, rather 
   than demonstrating that it works. Boris Beizer expanded on path testing, data 
   flow testing, and state transition models. Roger Pressman and Ian Sommerville 
   codified the division between Verification ("Are we building the product right?") 
   and Validation ("Are we building the right product?").

2. IEEE 829 Standard for Software Test Documentation:
   The IEEE 829 standard outlines the structure of formal test documentation, 
   specifying 14 mandatory sections for test planning, test case specification, 
   test procedure specification, and test summary reporting. This standard 
   ensures transparency, auditability, and clear exit/suspension criteria.

3. Black-Box Test Design Methodologies (BCS BS 7925-2):
   Equivalence Partitioning (EP) and Boundary Value Analysis (BVA) are two of 
   the most established specification-based testing techniques. EP reduces an 
   infinite input domain into finite equivalence classes, while BVA targets 
   the boundary conditions where empirical software defects disproportionately cluster.

4. White-Box Code Coverage Metrics (Miller, McCabe):
   White-box coverage criteria originated with statement and branch coverage. 
   Thomas McCabe introduced Cyclomatic Complexity to measure linearly 
   independent paths through a program's control flow graph. Statement 
   coverage ensures every line is executed at least once, while branch coverage 
   requires every boolean decision outcome (True and False) to be evaluated.

5. Modern Test Automation Frameworks:
   The evolution from Selenium WebDriver to modern browser automation 
   architectures (Playwright, Puppeteer, Cypress) represents a shift toward 
   devtools-protocol-based automation. Playwright provides native async 
   execution, fast headless Chromium/Firefox/WebKit execution, auto-waiting, 
   and deterministic screenshot and network inspection.

6. Defect Lifecycle & Quality Models (ISO/IEC 25010):
   ISO/IEC 25010 defines software product quality through functional suitability, 
   reliability, usability, performance efficiency, and maintainability. Defect 
   tracking models structure the transition of defects through distinct states, 
   preventing premature bug closure through formal retest phases.


2.2 RELEVANCE
The reviewed literature and standards directly inform the architectural design 
and functional implementation of TestLab:
- Architecture Choice: A modular monolith built with FastAPI and SQLite was 
  selected to satisfy the educational need for complete transparency, zero 
  cloud dependencies, and low setup friction while offering asynchronous API 
  speed and Pydantic validation.
- Curriculum Fidelity: The ten experiments in TestLab directly align with 
  university syllabus requirements while eliminating the historical flaw of 
  teaching black-box/white-box techniques as disconnected textbook exercises.
- Standardized Reporting: Implementing the ReportLab PDF compiler ensures that 
  every test plan and final report strictly complies with the 14-clause IEEE 829 
  structure, training students in industrial documentation standards.
- Authentic Execution: Rather than providing mock success messages or hardcoded 
  chart data, TestLab invokes actual Pytest subprocesses, Coverage.py runs, and 
  headless Playwright browser sessions, providing authentic, verifiable results.

3.1 INTRODUCTION
System Analysis involves evaluating the operational requirements, user roles, 
architectural constraints, and functional specifications necessary to build an 
integrated Software Testing laboratory platform. The analysis establishes how 
the functional applications interact with the laboratory testing modules and 
data persistence layer.


3.2 PROBLEM DEFINITION
The system must resolve the disconnect between developing software and testing 
it. Specifically, the software must provide:
1. Multi-role user access (Student/Tester vs. Teacher/Admin) with session-based 
   authentication and Bcrypt password hashing.
2. Complete data persistence in SQLite ensuring that tasks, marks, student records, 
   defects, test runs, and test plans remain intact across sessions.
3. Strict user-level data isolation preventing users from modifying or viewing 
   other users' private tasks.
4. Dynamic calculation of all metrics and chart statistics directly from the 
   SQLite database records.
5. Independent access to each of the 10 experiments without prerequisites.
6. Sandbox safety preventing arbitrary or untrusted remote code execution while 
   allowing verified execution of predefined Pytest and Playwright suites.

3.4 SYSTEM REQUIREMENTS ANALYSIS

3.4.1 Functional Requirements (FR)
- FR-01: User Authentication & Role Management:
  Registration, login, logout, Bcrypt hashing, secure session tokens, protected 
  endpoints, and role-based permissions (Student vs. Teacher).
- FR-02: To-Do List Management System:
  Task creation, title length validation (3–100 chars), description limits (500 chars), 
  priority levels (Low, Medium, High), status toggling (Pending, In Progress, Completed), 
  date-based due dates, searching, multi-filter queries, and user isolation.
- FR-03: Student Result Management System:
  Student enrollment, subject marks entry (0.0 to 100.0 inclusive), arithmetic total, 
  percentage calculation, grading rubric (A: 90-100, B: 80-89, C: 70-79, D: 60-69, 
  F: 0-59), and pass/fail determination (minimum 40 marks per subject).
- FR-04: Software Testing Laboratory (10 Experiments):
  Dedicated workspaces for all 10 curriculum experiments with 4 unified tabs.
- FR-05: Defect Tracking & Kanban System:
  Full defect attributes, 7-stage status workflow, severity/priority filtering, and 
  automatic reversion to Open upon retest failure.
- FR-06: SQA Metrics Engine:
  Real-time calculation of Defect Density, Defect Rate, and Productivity with 
  configurable work units, and exact syllabus dataset benchmark evaluation.
- FR-07: Automated Test Execution:
  Subprocess execution of Pytest test suites (unit, integration, API, regression) 
  and headless Chromium Playwright browser workflows.
- FR-08: Code Coverage Measurement:
  AST statement and branch coverage via Coverage.py.
- FR-09: Report Generation:
  Compilation of downloadable IEEE 829-standard PDF reports.

3.4.2 Non-Functional Requirements (NFR)
- Performance: Dashboard API queries resolve in under 50ms; automated test execution 
  duration is recorded in seconds.
- Security: Passwords hashed with bcrypt and random salt; session tokens signed with 
  HMAC-SHA256; SQL injection prevented via SQLAlchemy parameterized queries; XSS 
  prevented via Jinja2 auto-escaping.
- Reliability: Database foreign keys enforced via SQLite connection pragmas; unhandled 
  exceptions caught and serialized to JSON error responses.
- Usability: Clean SaaS dark and light themes, responsive Bootstrap 5 layout, 
  mobile drawer navigation, and accessible typography.

3.4.3 Software & Hardware Requirements
- Operating System: Windows 10/11, Linux (Ubuntu 20.04+), or macOS.
- Language & Runtime: Python 3.12 (or 3.10+).
- Backend Framework: FastAPI 0.110+ with Uvicorn ASGI server.
- Database: SQLite 3 with SQLAlchemy 2.0+ ORM.
- Automation Engines: Pytest 9.x, Playwright 1.42+ (Chromium), Coverage.py 7.x.
- Documentation Engine: ReportLab 5.x.
- Frontend Technologies: HTML5, CSS3, JavaScript (ES6+), Bootstrap 5.3, Chart.js 4.4.
- Hardware: Minimum 4 GB RAM, 2 GHz Dual-Core CPU, 2 GB available disk space.

4.1 DESIGN METHODOLOGY
TestLab follows domain-driven, modular design principles. The backend is 
organized into separated layers:
- Configuration (`app/config.py`): Centralized environment settings and directory paths.
- Database Connection (`app/database.py`): SQLAlchemy engine with SQLite foreign-key 
  pragmas and session generator.
- Data Models (`app/models/`): Strongly typed SQLAlchemy relational definitions.
- Schemas (`app/schemas/`): Pydantic validation models enforcing strict data constraints.
- Services (`app/services/`): Pure business logic isolated from HTTP transport.
- Routers (`app/routers/`): Modular REST API endpoints and server-rendered HTML page routes.
- Templates & Static (`app/templates/`, `app/static/`): Modern Jinja2 templates and assets.

CHAPTER 5: SYSTEM IMPLEMENTATION

5.1 INTRODUCTION
The implementation phase translates the architectural blueprints into functional, 
robust, and well-tested code. TestLab was developed strictly adhering to 
Python 3.12 best practices, async FastAPI endpoints, SQLAlchemy relational 
declarations, Pydantic data contracts, and vanilla JavaScript ES6 frontend 
components.


5.2 IMPLEMENTATION OF PROPOSED METHODOLOGY

5.2.1 Backend Architecture & Database Engine
- `app/database.py`: Establishes the SQLAlchemy engine. Uses the SQLite connection 
  hook `@event.listens_for(engine, "connect")` executing `PRAGMA foreign_keys=ON` 
  to enforce referential integrity.
- `app/dependencies.py`: Defines `get_current_user` dependency supporting both 
  browser session cookies (`testlab_session`) and programmatic API tokens (`Bearer`).
- `app/seeder.py`: Runs automatically upon application startup to create tables 
  and seed default users (`student@testlab.edu`, `teacher@testlab.edu`), all 10 
  experiments, 55 baseline test cases, demo tasks, and defects.

5.2.2 To-Do List Management System (FR-02)
- Implemented in `app/services/task_service.py` and `app/routers/tasks.py`.
- Supports complete CRUD with title validation (3–100 characters), description limits 
  (500 characters), priority enumeration (`Low`, `Medium`, `High`), and status 
  workflows (`Pending`, `In Progress`, `Completed`).
- Implements strict user isolation: `db.query(Task).filter(Task.id == task_id, Task.user_id == user_id)`. 
  Users can never view or manipulate another user's task records.

5.2.3 Student Result Management System (FR-03)
- Implemented in `app/services/student_service.py` and `app/routers/students.py`.
- Validates marks to be numeric floats within $[0.0, 100.0]$. Rejects negative 
  marks, values $>100$, and empty strings.
- Pure grading logic:
  - Percentage $\ge 90.0\%$: Grade A
  - Percentage $\ge 80.0\%$: Grade B
  - Percentage $\ge 70.0\%$: Grade C
  - Percentage $\ge 60.0\%$: Grade D
  - Percentage $< 60.0\%$: Grade F
- Pass/Fail rule: A student Passes if and only if each individual subject mark 
  is $\ge 40.0$ AND the overall percentage is $\ge 40.0\%$. If any single subject 
  falls below 40 marks, the outcome is strictly Fail.

5.2.4 Ten Independent Experiment Modules (EXP 01 to EXP 10)
- EXP 01 (Division & Estimation): `experiments/exp01_intro/`. Implements safe 
  division with ZeroDivisionError exception handling, intentional bug activation 
  demo, and interactive comparative Waterfall vs. Agile schedule modeling.
- EXP 02 (Test Planning & Checklists): `experiments/exp02_test_planning/`. 
  Static 5-point verification checklist and dynamic test suite (TC01–TC06) 
  executing live against the FastAPI authentication endpoint.
- EXP 03 (Defect Tracking & Age): `experiments/exp03_defect_tracking/`. 
  Boundary validator for age eligibility $[18, 60]$ and connection to the Kanban board.
- EXP 04 (Black-Box & Coverage): `experiments/exp04_black_box/`. ATM cash 
  withdrawal state machine supporting ₹100, ₹500, ₹1000 denominations, and a 
  syntax-highlighted code coverage tracer.
- EXP 05 (Integration & Metrics): `experiments/exp05_integration/`. Progressive 
  5-level top-down integration harness substituting stubs (`AuthStub`, `TaskStub`, 
  `DatabaseStub`) with real modules, plus Defect Density and Productivity calculators.
- EXP 06 (Metrics & 10 Phases): `experiments/exp06_metrics/`. Evaluates the official 
  syllabus dataset ($100\text{ KLOC}, 50\text{ defects}, 500\text{ hours}$) and 
  tracks all 10 testing lifecycle phases mapped to the Student Result System.
- EXP 07 (SRS & IEEE 829 Plan): `experiments/exp07_result_requirements/`. Functional 
  specifications (SRS-FR-01 to FR-06) and non-functional requirements, with a 
  dedicated IEEE 829 PDF test plan generator.
- EXP 08 (White-Box EP, BVA & Coverage): `experiments/exp08_white_box/`. Valid 
  and invalid Equivalence Partitioning matrices, 3-point Boundary Value Analysis 
  around 0, 60, 70, 80, 90, 100, and live Coverage.py execution.
- EXP 09 (Playwright Automation): `experiments/exp09_automation/`. Async Playwright 
  runner launching headless Chromium to test login, empty validation, invalid 
  credentials, valid redirect, and logout, saving real screenshots to `/evidence/`.
- EXP 10 (Final Project Case Study): `experiments/exp10_final_project/`. Master 
  orchestrator evaluating all 12 testing methodologies against the To-Do platform.

5.2.5 Modern Responsive SaaS User Interface & Dashboard
- Styled with custom CSS variables in `app/static/css/styles.css` supporting 
  dynamic Dark and Light theme switching via localStorage.
- Dashboard initialized in `app/static/js/dashboard.js` rendering Chart.js 
  doughnut and bar charts populated from `/api/metrics/summary`.
- Interactive 7-column Kanban board in `app/templates/defects.html` with real-time 
  defect status updates and retest logic.

5.2.6 Test Execution, Playwright Automation & Coverage Engines
- `app/services/test_executor.py`: Spawns Python subprocesses executing Pytest 
  suites, parses stdout/stderr lines for passed/failed counts, persists results 
  into `test_runs` in SQLite, and streams logs to the UI terminal emulator.
- `app/services/coverage_service.py`: Uses the Python `coverage` library with 
  `branch=True` to inspect AST execution paths and extract line-by-line metrics.

5.2.7 ReportLab IEEE 829 PDF Generation Service
- Implemented in `app/services/pdf_generator.py`.
- Formats structured PDFs using `SimpleDocTemplate`, `Table`, `TableStyle`, and 
  custom typography adhering to the 14 standard clauses of IEEE 829.

CHAPTER 6: SYSTEM TESTING AND TEST CASES
================================================================================

6.1 TYPES OF TESTING
TestLab evaluates and executes 12 distinct software testing methodologies 
against its functional modules:

1. Unit Testing:
   Verifies individual functions, classes, and helper algorithms in complete isolation.
   Target: Task CRUD operations in `task_service.py`, grading rules in `student_service.py`, 
   and metric calculations in `metrics_service.py`.

2. Integration Testing:
   Verifies that communicating modules interact properly according to architectural 
   interfaces.
   Target: Top-Down hierarchy substituting stubs with live SQLite database connections.

3. Functional Testing:
   Evaluates system behavior against specified functional requirements (FR-01 to FR-04).
   Target: Complete To-Do task management workflows and Student Result calculations.

4. System Testing:
   Evaluates the end-to-end integrated application against comprehensive business requirements.
   Target: Full multi-user navigation, database updates, session management, and PDF exports.

5. Black-Box Testing:
   Validates inputs against expected outputs without examining internal code structures.
   Target: ATM withdrawal denomination checks, candidate age limits, and login boundary inputs.

6. White-Box Testing:
   Analyzes internal logic paths, decision branches, and statement coverage.
   Target: Coverage.py AST branch and statement analysis of `calculate_grade`.

7. Regression Testing:
   Re-executes test suites after code modifications to ensure no existing functionality breaks.
   Target: Automated Pytest regression suite in `tests/regression/test_regression.py`.

8. Smoke Testing:
   Critical build verification tests run immediately to ensure major platform functions operate.
   Target: FastAPI `/api/auth/me` and `/dashboard` availability checks.

9. Sanity Testing:
   Targeted validation verifying that specific bug fixes or minor alterations function as intended.
   Target: Retest state verification and boundary validation checks.

10. API Testing:
    Validates REST endpoint status codes, payload structures, HTTP verbs, and headers.
    Target: FastAPI TestClient test suite in `tests/api/test_api_contracts.py`.

11. UI Automation Testing:
    Simulates human user interactions at the browser DOM level.
    Target: Playwright headless Chromium browser test suite in `tests/ui/`.

6.3 DEFECT REPORTING AND TRACKING

6.3.1 Defect Taxonomy and Attributes
Defects in TestLab are formally documented with the following standard attributes:
- Defect Identifier: Unique auto-generated alphanumeric key (e.g., `DEF-0001`).
- Title: Concise summary of the observed malfunction.
- Description: Detailed technical context and error output.
- Steps to Reproduce: Step-by-step instructions to reproduce the failure.
- Expected Result: Expected specification-compliant behavior.
- Actual Result: Actual aberrant runtime behavior observed.
- Severity: Impact rating (`Critical`, `High`, `Medium`, `Low`).
- Priority: Resolution urgency (`P1`, `P2`, `P3`, `P4`).
- Current Status: Position in lifecycle (`New`, `Assigned`, `Open`, `Fixed`, `Retest`, `Verified`, `Closed`).
- Assigned Person: Engineer responsible for remediation.
- Timestamps: Date created and updated.

6.3.2 7-Stage Defect Lifecycle Implementation
The defect state machine strictly enforces legitimate state transitions:
1. `New`: Newly submitted bug awaiting triage.
2. `Assigned`: Assigned to development team.
3. `Open`: Acknowledged and under active investigation.
4. `Fixed`: Developer has applied patch; code deployed to test environment.
5. `Retest`: QA Engineer verifies the fix against reproduction steps.
   - **Retest Failure Rule**: If the verification fails, status reverts directly to `Open`.
   - **Retest Success**: If verification passes, status advances to `Verified`.
6. `Verified`: Confirmed resolved in test environment.
7. `Closed`: Final sign-off and defect closure.

6.4 TEST METRICS AND QUALITY MEASUREMENT

6.4.1 Quality Metric Mathematical Formulations
Software Quality Assurance metrics quantify quality attributes:

1. Defect Density:
   Measures defect concentration relative to code size.
   $$\text{Defect Density} = \frac{\text{Total Detected Defects}}{\text{Software Size in KLOC}}$$
   Unit: defects per KLOC.

2. Defect Arrival Rate:
   Measures defect discovery frequency over time.
   $$\text{Defect Rate} = \frac{\text{Total Detected Defects}}{\text{Total Testing Effort in Hours}}$$
   Unit: defects per hour.

3. Developer Productivity:
   Measures work throughput per unit of engineering effort.
   $$\text{Productivity} = \frac{\text{Completed Work Units (KLOC / FP / Test Cases)}}{\text{Total Working Hours}}$$
   Unit: work units per hour.

4. Test Execution Rate:
   $$\text{Execution Percentage} = \left(\frac{\text{Executed Test Cases}}{\text{Total Test Cases}}\right) \times 100\%$$

5. Test Pass Rate:
   $$\text{Pass Rate} = \left(\frac{\text{Passed Test Cases}}{\text{Executed Test Cases}}\right) \times 100\%$$

6.4.2 Official Syllabus Benchmark Dataset Evaluation
Using the exact academic syllabus dataset:
- Software Size: $100\text{ KLOC}$
- Total Defects: $50\text{ Defects}$
- Testing/Development Effort: $500\text{ Hours}$

Calculated Metric Values:
- $\text{Defect Density} = \frac{50}{100} = \mathbf{0.5\text{ defects/KLOC}}$
- $\text{Defect Arrival Rate} = \frac{50}{500} = \mathbf{0.1\text{ defects/hour}}$
- $\text{Productivity} = \frac{100}{500} = \mathbf{0.2\text{ KLOC/hour}}$

Interpretation:
The software exhibits an average density of 0.5 defects per 1,000 lines of code. 
Defects were uncovered at an arrival rate of 0.1 defects per working hour (1 defect 
every 10 hours). Engineering productivity averaged 200 lines of delivered code 
per hour of effort.
